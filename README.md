# edu-attendance-tracker

Расписание, подсчёт людей на фото и видео, замеры занятий и отчёты по группам.
Проект **не определяет личности** и не подтверждает присутствие конкретного студента.

**React / TypeScript** · **FastAPI** · **PostgreSQL** · **S3 / MinIO** · **YOLO**

## Откуда Данные И Куда Они Идут

```mermaid
flowchart LR
    X[Расписание XLSX] -->|проверка и подтверждение| API[FastAPI]
    F[Фото / видео] -->|загрузка| API
    API -->|файл| S3[(S3 / MinIO)]
    API -->|записи и задания| DB[(PostgreSQL)]
    DB -->|очередь| R[Recognition / YOLO]
    S3 -->|исходник| R
    R -->|метрики| DB
    R -->|размеченный кадр| S3
    DB --> A[Замеры и агрегация]
    A -->|итоги| DB
    DB -->|через API| UI[Интерфейс / графики / CSV]
```

1. **Расписание.** После проверки XLSX записи попадают в БД. Планировщик создаёт
   занятия и два замера: после начала и перед окончанием.
2. **Материалы.** API проверяет фото или видео, сохраняет исходник в S3 и создаёт
   задание в PostgreSQL. Ответ `202` означает принятие в работу, а не готовый результат.
3. **Распознавание.** Отдельный worker получает задание и файл. YOLO ищет людей
   на выбранных кадрах; итог видео считается по медиане. Метрики сохраняются
   в БД, размеченный JPEG — в S3.
4. **Отчёты.** Результат, привязанный к замеру, участвует в итогах занятия.
   Интерфейс получает данные через API; изображения — по временным ссылкам.

Камерный путь подключается отдельно: **RTSP → FFmpeg → S3 → очередь распознавания**.
Фото и видео можно загружать без камер. [Подробные связи и гарантии](docs/architecture.md).

## Три Режима

| Режим | Что работает | Что не следует из показа |
| --- | --- | --- |
| Статическое демо | Учебное расписание, роли интерфейса, графики и CSV | Нет серверной авторизации; числа заданы в примере |
| Локальное распознавание | Свой файл обрабатывается через ONNX/WASM на устройстве | Файл не отправляется на сервер; качество требует проверки |
| Полный стенд | Вход, доступ по ролям, загрузка, очередь и история результатов | Нужны БД, S3, веса модели и HTTPS |

При ошибке модели интерфейс не подставляет готовое число. Для демо и рабочего
стенда используются отдельные окружения, базы, хранилища и учётные данные.

## Быстрый Старт Без Контейнеров

Нужны Node.js 24 (в CI закреплён 24.21.0) и npm. Из корня репозитория:

```bash
cd frontend
npm ci
npm run dev:demo -- --host 127.0.0.1 --port 4173 --strictPort
```

Открыть `http://127.0.0.1:4173/#/`. Ожидается синтетический обзор с меткой
«Учебный пример». При занятом порте выбрать другой; Ctrl+C останавливает сервер.
Перезагрузка страницы сбрасывает изменения учебного примера.

Свой файл можно проверить в «Распознавание» → «Проверить файл».
Нужен современный браузер с Worker, OffscreenCanvas и Web Crypto; страница должна
быть открыта через localhost или HTTPS. При первом запуске загружаются файлы модели.
Используйте только материалы, на обработку которых у вас есть разрешение.

## Серверный Контур

Запуск требует закреплённых образов, отдельных прав БД и хранилища, HTTPS,
проверенных весов модели и границ семестра. Паролей «по умолчанию» нет.
Порядок подготовки, запуска и восстановления: [эксплуатация](docs/operations.md).

Справка по командам, без запуска сервисов:

```bash
python3 scripts/ops/manage.py --help
python3 scripts/ops/data.py --help
```

Вход использует HttpOnly cookie и защиту CSRF. Загрузка файла и повторная обработка
требуют `Idempotency-Key`, чтобы повтор запроса не создавал дубликаты.
[Примеры запросов](docs/api.md).
Первый администратор создаётся командой `python -m app.admin USERNAME` из
`backend/` в подготовленном окружении; пароль вводится в терминале.

## Проверки

Из `frontend/`: `npm run typecheck`, `npm run lint`, `npm test`,
`npm run build`, `npm run build:demo`, `npm run test:e2e`.
Зависимости и параметры тестовых БД описаны в [инструкции по тестированию](docs/testing.md).

После установки зависимостей схем:
`npm --prefix docs/diagrams run render`,
`npm --prefix docs/diagrams run check`,
`npm --prefix docs/diagrams run links`.
Каждый результат CI относится к конкретному коммиту.
